# Native Party group reservations V1

This optional path extends the existing Party, dedicated-server queue, and join owners. It keeps protocol57 and all existing packet layouts. It does not replace server admission or grant peer authority.

The dedicated server opts in with `PartyReservationsEnabled` (or `PROJECT_PRIME_PARTY_RESERVATIONS_V1=1`). Capability remains off until the existing reporter credential owner successfully verifies backend V1 support. Optional status flag2 advertises availability. Old servers/clients continue ordinary solo/FIFO behavior; an explicit captured group intent never silently falls back to solo admission.

The leader must already own a server-verified persistent Lobby. Native Party Reserve captures current self, Party revision, travel ID/revision, match, epoch and account lease. The existing backend reservation/member rows hold the immutable cohort and fixed request deadline. Backend intent is displayed as intent. Only live server acknowledgement of successful backend activation plus current local slot holds produces Reserved. Reserved and Admitting never mean Joined.

## Capacity and packets

The existing `LobbyWaitlist` owns all singles and groups in one FIFO and one reserved-slot mask. Groups take all missing seats or none. Older solo offers are preserved; an unsatisfied group at the head blocks newer entries until its fixed deadline (maximum20seconds). Tentative activation holds count against humans, bots, campaign slots and direct joins. Local activation holds are at most15seconds and clipped to their original deadlines. Cancellation releases remaining unadmitted seats; admitted players remain owned by the ordinary session.

Only new packet IDs80 Request,81 State,82 Action are added. They are established, reliable Critical control traffic with explicit queue direction allowlists. They are never unsequenced/bootstrap packets. The maximum request payload is929bytes (957 including24-byte envelope and4-byte reliable event ID), under1472. Canonical bounded UUID strings, tickets<=768bytes, exact ClientId/queue nonce/connection incarnation, match/epoch and monotonic state revisions fence requests. Correlation nonces do not authenticate accounts.

The existing enabled-reporter key and pp1 HMAC verifier establish the account and client binding. Current verified membership receipts reconcile already-present Party members with actual local peers; UDP names/PPIDs are never trusted as identity. Per-connection start cooldown, eight workers, existing unproven/bootstrap limits and fixed operation deadlines bound control-plane work.

## Admission and cancellation

The existing queue socket is retained through QueueHello/QueueWelcome, explicit group attachment, Accept, ordinary Welcome, `TakeAdmission`, `NetLaunch.Connect(queuedAdmission)` and the existing root `CanAccept -> AcceptJoin -> Note` handoff. Group mode sends MemberAttach instead of ordinary QueueJoin. No second gameplay pump or socket replacement is introduced.

Ticket acquisition happens before queue creation. The existing absolute5-second unproven server lifetime remains; verification has at most3.5seconds, clipped to CreatedAt+4.5seconds. Only a successfully verified attachment leaves the unproven state. Verified attachments do not consume the16-unproven budget.

Backend `claim_admission` is the cancellation linearization point. A claim lasts at most2seconds and is bound to reporter, request, member, slot, connection incarnation and nonce. Cancel before claim rejects admission. A claim already committed may settle after cancellation within its original deadline. It is not Joined. The actual server peer must exist before the admitted acknowledgement; the acknowledgement is observed/retried under its original proof without creating another peer or stopping the accepted session. A missing first acknowledgement after claim expiry remains a backend failure, not invented admission.

Busy worker pools retain one bounded pending Accept identity until its original short deadline, then explicitly expire it. Cancellation uses the known real reservation ID even if the activation reply has not arrived, and retains bounded cleanup retries. Delayed activation replies cannot restore cancelled local holds. Backend operation deadlines and tombstones prevent late mutation from reviving cancelled requests. No distributed HTTP/UDP atomicity is claimed.

Account-sensitive local effects use the existing auth Gate before the existing client lifecycle gate. Bounded queue creation/Poll/action sends and join initialization are fenced; HTTPS and the join pump remain outside the local action callback. The career ticket cache retains the opaque producing lease and invalidation generation, so a held old-account completion cannot publish into a replacement account. Leader reservation state stores only a weak opaque witness, strips the stored ticket after send, and clears on Stop/Rebind.

The native joining route owns the visible queue card through its existing Join job. It reads immutable memory-only snapshots and issues exact captured commands. The worker does not replace a snapshot merely because its countdown ticks; a queued action also retains its wire revision so a later state cannot reinterpret an old click. Foreground document and account retirement fences remain in the existing owners.
