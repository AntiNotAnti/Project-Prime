# Project Prime engineering audit and implementation roadmap

Audit date: October 5, 2026, America/Chicago. Repository: AntiNotAnti/Project-Prime. Source of truth: main at **a68627d0f7299c873cce9ad8046afbc6af0c46d5**. Remote main still matched that commit at the final repository check. Initial open-PR checks were empty; the final check found **PR #347**, reviewed separately at head `7f1716391b1ec87dff4f08fe5264abd54992ecc9` in section 13. Its base matches the audited main snapshot.

## 1. Executive summary

**Project Prime has substantial working infrastructure, but this main revision is not release ready.** The unmodified desktop Release build fails with six compiler errors in recently added alternate-form and halfturret acceptance checks. The current main CI run already has 25 failed jobs. The server conditional build succeeds, and its missing-assets smoke test correctly verifies exit status 1 and absence from the directory. This is a frozen main snapshot: ongoing agent work may repair the build before the roadmap is implemented. Recheck main and use a forced clean build before treating any standalone green check as evidence of overall readiness.

The largest risks are ownership and trust at integration boundaries. Android drops scenes without releasing static managed model leases; the desktop multi-draw atlas never reclaims released room geometry; the collision pool adds 2,048 objects on every scene initialization. Map installation has cancellation and publication paths that bypass safeguards implemented elsewhere. Replay metadata loses the exact custom-package identity needed before construction, and initial checkpoint failures can leave a partially restored world in use. Combat claims can become authoritative outcomes without establishing that the claimed attack launched; ordinary inventory and powerup reports also remain client authored.

Several mundane failures deserve early fixes: the updater continues when the old process is still alive, a local release manifest can delete neighboring files, the macOS packaging fixture no longer satisfies its own wrapper, Forge Pop Out conflicts with the client instance guard, animated project export misses flipbook paths, and a moderation catalog can save a state that prevents the Community service from restarting. These have clearer benefit than another large rendering or networking redesign.

The performance conclusions are deliberately narrower than the bug conclusions. Cumulative pool/atlas retention, undercounted replay capacity, repeated replay decompression and large package copies are visible in the implementation. Their actual contribution to frame spikes, launch time or device memory pressure still needs workload measurement. There is no defensible percentage FPS gain or measured ranking of cold-start milliseconds in this audit. The current render throughput harness also cannot establish real 1% lows because its timing excludes presentation and repeats draws of one fixed simulation state.

## 15. Major opportunities

**Combat evidence and legal resource authority** is the highest integrity investment. B08/B09 need coordinated shot/pickup policy plus a realistic latency/contact matrix. Keep successful local rescues and current movement; implement the minimum bounded ledger before considering protocol changes.

**Reliable platform resource ownership** combines Android scene/surface lifetimes, atlas reclamation and complete accounting. It can reduce session-length instability and makes future renderer work measurable. This is more valuable than adding more GPU features before existing culling/reclamation is conservative.

**Exact, versioned replay worlds** can make Studio a dependable diagnostic/export tool. Correct mandatory origin, identity and candidate transactions first, then shared chunk reads and staged owner construction. Historical support needs explicit schemas and archived fixtures, not permissive hash exceptions.

**Bounded Community service growth** joins restartable catalogs, upload reservations/expiry, control-plane isolation and streamed package handling. Begin with deterministic limits and narrow indexing; move to indexed persistence only after supported-load benchmarks justify it.

**Trustworthy end-to-end timing** turns startup and frame discussions into comparable evidence. Extend existing telemetry/LifecycleTiming with actual present, phase/GPU timing, capacity and process-release boundaries. This investment has no promised direct FPS gain; it prevents costly work on the wrong bottleneck.

**Safe UI modernization** uses those service/ownership contracts so Avalonia and RmlUi are interchangeable adapters. Ship surface-sized changes with focus/navigation/rendered tests. No all-at-once launcher rewrite or new render engine is supported by current evidence.
