# Authoritative bot fill

Bot fill is opt-in: `PRIME_BOT_FILL=4` targets four total participants, and `PRIME_BOT_SKILL=0`, `1`, or `2` selects the existing Hunter AI level (default 1). The target must fit the match capacity. No humans means no new bots. Observers do not count as humans. Reconnect-reserved slots remain reserved.

`ServerBotManager` owns at most eight `BotParticipant` records. Each uses a normal player slot, Hunter, team, statistics and random nonzero combat identity; it creates no `NetConnection`, socket, reliable queue or client input stream. Current-tick attribution explicitly prevents inherited human latency/input from rewinding bot shots. Existing Scene headless AI input and processing run the same Hunter AI. Dynamic activation loads the mode-specific personality before spawning. AI level selects existing aim deviation/tracking, charge/weapon decisions and movement timing; this slice changes no health, damage, weapon cooldown or movement speed values. No new personality or omniscient targeting policy is introduced.

Human admission asks the controller to claim an otherwise free slot. A bot can retire immediately while waiting/counting down, or when dead during play. A join first prefers an empty slot; otherwise it requests exactly one bot retirement and reserves that slot in a bounded eight-entry admission queue. Nonce-bound protocol 8 `JoinPending` messages keep the pinned client handshake alive for at most 30 seconds, with the normal retry heartbeat timeout. Validated ticket identity is retained without consuming the ticket again and its expiry is rechecked before admission. Cancellation, timeout or match rotation releases the reservation and retirement request. Bot fill cannot refill a reserved slot. Discovery v3 advertises bot count separately; full-server filtering counts humans, so a bot-filled server remains discoverable. Retirement calls authoritative objective release (nodes, carried flags and Prime Hunter), freezes any report interval, deactivates the body and clears slot statistics before reuse. A live carried objective is never simply deleted. Excess bots retire using the same boundary. Team selection balances current humans and bots when adding a bot.

Live protocol 8 roster entries add an explicit final byte (`0` human, `1` bot), making each entry 30 bytes. Protocols 5–7 retain their frozen 29-byte demo adapter. Terminal PlayerIdentity C uses bit 0 for active and bit 1 for bot; other bits are rejected. Clients retain bot metadata without enabling local AI for replicated players. Postmatch rows mark bots, and immutable reports use `ParticipantKind.Bot` with no authenticated PlayerId. Bots are not official player accounts or rating recipients.

The desktop host card offers **Practice with bots**: a separate authoritative server process bound only to localhost, unlisted, with a four-participant target and default skill. The child joins through the normal UDP client. Its reporting and ticket configuration is removed from the child environment, so Practice cannot accidentally submit official reports. Android continues to join dedicated authoritative servers; it does not embed a second offline/server simulation.

Validation uses the actual Sanctorus content: activation, normal snapshots/combat identities, twenty simulation ticks of existing AI, safe-death retirement, Prime objective release and bot report identity. Pure tests cover population bounds and invalid skill, explicit roster flag validation and terminal identity flag validation. Test logs are `/tmp/codex-re-prime-g5-bots-tests.log` and `/tmp/codex-re-prime-g5-bot-probe.log`; build log `/tmp/codex-re-prime-g5-bots.log`. A rendered Practice session and subjective skill/readability assessment still require a real client run; source or headless tests do not claim those results.
